01 The problem

Team-owned services still behaved like a distributed monolith.

I had seen the system grow from a monolith into team-owned microservices as engineering scaled past roughly 50 people. Service-to-service communication was still ad hoc: direct calls, custom payloads, and team-specific retries.

Grounding · ownership shift
Before the bus, the producer had to own everyone else's workflow.

Service A had to know which services cared about a policy change, how to call them, and what to do when one dependency failed. Eventing changed that: Service A emits a durable business fact, and each consumer owns its reaction.

Downstream orchestration
calls, retries, responses

Owns downstream calls, retries, and response contracts.

producer after
Durable business fact
state change and event

Owns the state change and the event it emits.

consumer after
Independent reaction
handler and failure policy

Owns its handler, failure policy, and operational behavior.

04 Rejected producer path

A dual write has a crash window.

Write the row, then publish the event. A crash between the two steps loses the event, and a producer library that does both still has the same window.

Grounding · why produce through Postgres
The producer API had to be easy to adopt.

We needed event production to be easy to adopt, high-throughput, ordered where needed, and strongly consistent. Every service already used Postgres, and every engineer understood database transactions, so services would produce events through Postgres.

Consistency

Commit state and event together

Postgres gave producers a transaction boundary they already understood.

Throughput

Publish after commit

Product code records the event. CDC handles broker publishing asynchronously.

Ordering

Group related events

Ordering keys let the platform preserve sequence where business workflows needed it.

05 Producer design

The outbox makes the event part of the transaction.

Product code writes two rows in one Postgres transaction. Platform code publishes them after commit.

GuaranteeCommit, and both rows exist. Roll back, and neither does. Product code never talks to Kafka.
Grounding · the outbox record
A normal Postgres row is the whole producer API.

The platform-owned monitor tailed committed rows, validated payloads, published them, and recorded progress. partition_key groups related events for ordering. failure_strategy decides whether a failing event blocks later work.

outbox_events
CREATE TABLE outbox_events (
  id UUID NOT NULL DEFAULT gen_random_uuid() PRIMARY KEY,
  name text NOT NULL,
  created_at timestamp with time zone DEFAULT CURRENT_TIMESTAMP NOT NULL,
  partition_key text,
  payload jsonb NOT NULL,
  source text NOT NULL,
  failure_strategy text CHECK (failure_strategy IN ('retry', 'drop', 'dlq')),
  delivered_at timestamp with time zone
);
06 Delivery contract

At-least-once delivery, so handlers are idempotent.

If the monitor crashes after publishing but before it records progress, it publishes the same event again.

07 Architecture

Kafka in the middle. HTTP at the edge.

Product teams own both ends. The platform owns everything in between.

10 Consumer design

Most teams just implemented an HTTP endpoint.

The dispatcher sidecar owned Kafka clients, offsets, and retries. Teams kept a normal handler, and could still consume Kafka directly if they needed control.

Grounding · dispatcher configuration
The shared dispatcher optimized for adoption, not maximum control.

v1 used SNS/SQS. v2 moved to Kafka/MSK for broker semantics, replay, and debugging. A Kafka client is a harder model, so Benthos delivered events to a local HTTP endpoint inside each pod.

    addresses: [ ... ]

pipeline:
  processors:
    - for_each:
      - mapping: |
          root.event_id = this.id
          root.name = this.name
          root.payload = this.payload

output:
  http_client:
    url: http://localhost:8080/events
    verb: POST
11 Failure policy

Teams chose what a failing event does to their partition.

failure_strategy is set per event path. Because a partition is processed in order, blocking and flowing are a real tradeoff.

detail
12 Operating reliability

CDC was the hardest reliability problem.

A stalled consumer holds its replication slot, and Postgres keeps the WAL until the slot catches up. Replication lag is a product reliability issue, not just an infra metric.

Grounding · split of responsibility
The platform owned delivery. Teams owned idempotency.

The normal delivery contract was at least once. Product teams made handlers safe for duplicates and chose a failure policy for each path.

platform-owned
CDC pipeline health
replication and outbox lag

Replication slot health, WAL growth, and publisher lag belonged to the platform.

team-owned
Idempotent handlers
duplicate-safe effects

A repeated event could not create an incorrect second business operation.

configured per path
Failure strategy
retry, DLQ, or drop

Teams chose whether a failing event blocked its partition, moved aside, or was discarded.

Grounding · production evolution
I built the first publisher against the WAL, then moved the platform toward Debezium.

The first version used a custom WAL monitor because I did not yet know about Debezium. It proved the outbox design, but it also made replication behavior platform code we had to own. Moving toward Debezium kept the producer and consumer contracts intact while replacing custom CDC machinery with a purpose-built tool.

15 Retrospective

2021 → 2026: what I would do differently.

In 2021 I built a system any product engineer could use safely without becoming an infrastructure expert. Today I would give an agent the context and guardrails to help a strong engineer own more of it.

20212026
CDC
Migrated to Debezium, mainly to cut the bus-factor risk of complex WAL and Kafka queueing code.
→
Keep my Go monitor, which outperformed Debezium on our workload. An agent can explain it to a strong engineer.
Consumption
A Benthos HTTP sidecar for everyone, because learning Kafka was too big a lift.
→
Keep the sidecar as the default. Add a skill that teaches MSK IAM auth and scaffolds direct consumers.
Provisioning
Engineers read my Notion guide, then met with me to choose partitions. I applied the Terraform module.
→
A Slack agent runs that interview, opens the Terraform PR, and merges after approval.
Incidents
The owning engineer dug through dashboards by hand.
→
An incident agent with Datadog and code access correlates WAL growth, lag, DLQs, and deploys.
Schema changes
Producers and consumers coordinated by hand.
→
An agent finds every producer and consumer, checks compatibility, and sequences the rollout.
